# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
flutter pub get                 # install dependencies
flutter analyze                 # static analysis (must be clean before considering a change done)
flutter test                    # run all widget tests
flutter test test/widget_test.dart --plain-name "Hitting a bomb"  # run a single test by name
flutter run -d chrome           # run in Chrome (auto-launches a managed browser)
flutter run -d web-server --web-port=<port> --web-hostname=localhost  # run without auto-launching a browser (use this if -d chrome fails to launch; open the printed URL manually)
flutter run -d windows          # run as a Windows desktop app
dart run tool/generate_sounds.dart  # regenerate assets/sounds/{bomb,win}.wav if the synthesis parameters change
```

There is no lint-fix or format-check script beyond `flutter analyze`; the project uses the default `flutter_lints` rule set (see `analysis_options.yaml`).

**Adding a new dependency with a native/web platform implementation** (e.g. `flutter_tts`) requires a full stop-and-restart of any running `flutter run` session — hot reload (`r`) and even hot restart (`R`) only swap Dart code in the already-compiled bundle, they don't regenerate the web plugin registrant that wires the new platform channel up. Skipping the full restart doesn't error at build time; it fails silently at runtime with `MissingPluginException` on every call to the new plugin. If you (or the user) see that exception, the fix is a full stop + `flutter run` again, not a code change.

**"Failed to bind web development server" / `SocketException ... errno = 10048` on a fixed `--web-port`**: this means a *previous* `flutter run -d web-server`/`-d chrome --web-port=...` session is still holding that port — typically because it was stopped by killing the wrapping shell/task rather than letting `flutter run` shut down its own child process, which on Windows leaves the underlying `dartvm.exe` (the dev server) running and listening. Hot-reload/restart won't fix this since it's not even the same process anymore. Find and kill the leftover process rather than picking a different port every time:
```powershell
Get-NetTCPConnection -LocalPort <port> | Select-Object OwningProcess
Stop-Process -Id <OwningProcess> -Force
```

## Architecture

This is a Flutter **game platform** with Supabase as its backend (see "Repository abstraction" and "Kimlik doğrulama" below — Bombalı Sayılar persists results and the whole platform now gates behind Google sign-in): a `Navigator`-based shell that hosts multiple independent games — currently "Bombalı Sayılar", "Kart Eşleştirme", "Renk mi Kelime mi?", "Dizi Hafızası", "Diziler", "Tepki Süresi", "Simon Diyor ki", and "Kayan Yapboz". State management is `provider` (`ChangeNotifier` + `MultiProvider`), scoped **per game** — with the deliberate platform-wide exceptions of `ProfileController` and `AuthController` (see below).

### Platform shell and adding a new game

`main.dart`'s `GamePlatformApp` is a `MaterialApp` with `initialRoute: GameCatalogScreen.routeName` ('/') and an `onGenerateRoute` that maps route names to game root widgets. `screens/game_catalog_screen.dart` renders the home menu from the `gameCatalog` list (`GameCatalogEntry`: title/description/icon/color/routeName) — each card pushes its game's route by name via `Navigator.pushNamed`.

To add a new game:
1. Create `games/<new_game>_game.dart` with a root widget (see `games/bombali_sayilar_game.dart`) that owns a `static const routeName` and sets up that game's own `MultiProvider` scope (its controllers are created fresh on every navigation into the route and disposed on pop — game state never leaks between games or across a "leave and come back").
2. Add a case for that `routeName` in `main.dart`'s `onGenerateRoute`.
3. Add a `GameCatalogEntry` for it to `gameCatalog` in `screens/game_catalog_screen.dart`.
4. Give its setup screen a `widgets/player_count_selector.dart` (`PlayerCountSelector`, 1/2 players) and honor it consistently (see "Player count" below) — this is a platform-wide convention every game follows.
5. Give its `GameCatalogEntry` a `skills: GameSkillRatings(...)` (`models/game_catalog_entry.dart`) — 0-5 scores for Zeka/İngilizce/IQ/Hafıza, rendered as a 4-cell star table on the catalog card by `widgets/skill_ratings_table.dart`'s `SkillRatingsTable`. The field is `required`, so a new entry won't compile without it. Score honestly against what the game actually trains (e.g. only Kart Eşleştirme scores above 0 on İngilizce, since it's the only game with any English content); don't hide a 0 score by omitting that row — every card shows all four skills for a consistent table shape. The scores also drive the card's "… ODAKLI" chip via `GameSkillRatings.dominantSkillLabel`, which deliberately reuses one of those same four names (never a synonym like "MANTIK") so the chip can never contradict the star table right below it.

The platform-level `MaterialApp.theme` is a neutral fixed seed (`Colors.indigo`) — it does **not** react to any single game's theme picker. A game that wants its own live-selectable color scheme (as Bombalı Sayılar does) wraps its own subtree in a local `Theme(...)` fed by its own `AppThemeController`, scoped inside that game's root widget, not at the platform level.

### Home page look (`GameCatalogScreen` — dark "console panel")

The catalog is the one screen with a deliberately different visual identity from the rest of the platform: it applies its own dark theme (`theme/home_palette.dart`'s `HomePalette` + `homeThemeData()`) to its own subtree through a local `Theme(...)`, exactly the same escape hatch Bombalı Sayılar uses for its color presets. Game screens keep the light platform theme — **do not** move this dark theme up to `MaterialApp.theme`, it would repaint every game.

- **No `AppBar`.** The catalog is the root route, so it never needs a back button; a non-scrolling `_TopBar` (logo mark + "Oyun Platformu" + profile button) sits above the scroll view instead, so the title and profile button stay put while the list scrolls. The profile button is deliberately **icon-only** (`Icons.person` + a `Tooltip` carrying the name): rendering the profile name as visible text here would make `find.text('<name>')` match twice in tests that push a game on top of the catalog (a covered route's widgets stay findable), e.g. "Profildeki isim, oyunun 1. Oyuncu alanını otomatik doldurur". Keep the name out of the top bar's `Text` widgets.
- **Fixed-height card grid.** `_GameGrid` picks 1/2/3 columns from `LayoutBuilder` width (`_twoColumnWidth` 720 / `_threeColumnWidth` 1080) and pins every card to `_cardHeight` (234) via `mainAxisExtent`. The height is fixed on purpose — self-sizing cards produce a ragged bottom edge when placed side by side — so `widgets/game_card.dart` caps the description at 3 lines, the title at 1, and pushes the divider + star table to the bottom with a `Spacer`. **If you add a longer skill table, a subtitle, or a taller icon tile, raise `_cardHeight` too**, otherwise the card overflows (which is a hard failure in debug/tests, not just an ugly card).
- **The grid is `shrinkWrap` + `NeverScrollableScrollPhysics` inside a `SingleChildScrollView`**, not a lazy sliver: with only ~9 cards there is no perf reason for lazy building, and building all of them unconditionally is what makes the catalog widget tests independent of viewport height.
- `widgets/home_backdrop.dart` paints the whole background (gradient + faint grid + two radial glows) in a single `CustomPainter` with `shouldRepaint => false` — no image assets, so `pubspec.yaml` stays untouched.
- `homeAccentOf(color)` lightens/saturates a game's catalog color for use on the dark surface (icon tile gradient, focus chip, hover border, play affordance). Several catalog colors (brown, blueGrey, indigo) are unreadable on the dark backdrop untouched — always run a per-game color through this helper here rather than hand-picking a second color per entry.
- `widgets/star_rating.dart` uses a warm filled color against a very faint white empty color; on the dark backdrop the old "amber `star_border`" empty state was nearly indistinguishable from a filled star. `StarRating` is still the widget the catalog tests count (`gameCatalog.length * 4`), so keep four of them per card.
- **`LoginScreen` shares this identity**, since it's the screen right before the catalog: same `HomeBackdrop`, same `homeThemeData()`, same `widgets/platform_logo_mark.dart` (`PlatformLogoMark`, sized differently) and the same three `widgets/stat_chip.dart` badges via `platformStatChips()` (a top-level function in `game_catalog_screen.dart`, so the game count comes from `gameCatalog` and both screens update themselves when a game is added). These two are the only dark screens on the platform — everything behind the auth gate stays on the light platform theme. If you restyle one of them, restyle the other in the same commit or the sign-in → home transition visibly changes theme mid-flow.

### Screen flow (Bombalı Sayılar)

`games/bombali_sayilar_game.dart`'s `BombaliSayilarGame` wraps two `ChangeNotifierProvider`s (`GameController`, `AppThemeController`) around `_BombaliSayilarRoot`, which switches on `GameController.phase` (`GamePhase`: `setup → playing → turnTransition → finished`) to show `SetupScreen` / `GameScreen` / `TurnTransitionScreen` / `ResultsScreen`. Within this one game there are still no named sub-routes — adding a new screen to *this* game means adding a `GamePhase` value and a case in `_BombaliSayilarRoot`. Because the game is pushed via `Navigator`, every screen's `AppBar` gets Flutter's default back button for free, returning to the game catalog.

### Screen flow / rules (Kart Eşleştirme)

`games/memory_match_game.dart`'s `MemoryMatchGame` wraps a single `ChangeNotifierProvider<MemoryMatchController>` around `_MemoryMatchRoot`, which switches on `MemoryMatchController.phase` (`MemoryGamePhase`: `setup → playing → finished`, no `turnTransition` — turns pass silently since nothing needs to be hidden between hand-offs) to show `MemorySetupScreen` / `MemoryGameScreen` / `MemoryResultsScreen`.

- Grid is `gridColumns × gridRows` (4×4 = `pairCount` = 8 pairs, see `controllers/memory_match_controller.dart`); cards are two-per-symbol, shuffled fresh in `startGame`. Matching is still by `symbol` equality — each pair's two `MemoryCard`s additionally carry a different `label` (one gets the Turkish name, the other the English name), shown under the emoji on the front face as a lightweight vocabulary hook; this is purely cosmetic and never affects match logic.
- The setup screen's `widgets/memory_category_selector.dart` (`MemoryCategorySelector`) lets the player pick a `models/memory_category.dart` `MemoryCategory` (`fruits` or `vehicles`) before starting; `startGame(names, {required category})` looks up the matching symbol/name table via `_namesFor(category)` (`_fruitNames` has 12 entries, a random 8 are used per game; `_vehicleNames` has exactly 8 and all are used every game). To add a new category: add an enum value, a `_xxxNames` map with **at least `pairCount` (8)** entries, a case in `_namesFor`, and a segment in `MemoryCategorySelector`.
- `MemoryMatchController.flipCard` is the only mutator during play: a match keeps the turn on the same player (`currentPlayerIndex` unchanged) after a short reveal delay (400ms); a mismatch flips both cards back and advances `currentPlayerIndex` after a longer delay (850ms) so both players can see what was revealed. Both delays are guarded by a `_generation` counter bumped in `startGame`/`restart`, so a stale delayed callback from a game that was since restarted can't corrupt the new one's state.
- Winner = most `matchedPairs` (`MemoryMatchController.rankedByMatches`), the inverse ordering from Bombalı Sayılar's "fewest attempts wins".
- `widgets/memory_card_widget.dart` does the flip visual: a `TweenAnimationBuilder` drives a Y-axis `Matrix4` rotation between a fixed card-back face and the symbol face, matching the platform's general "make it feel 3D" direction (see the `grid_cell.dart` press/explode treatment in Bombalı Sayılar) — but this game intentionally has **no** `AppThemeController` integration; its fixed card-back color is a deliberate scope choice to avoid forcing a mismatched preset UI (the preset swatches literally render a sample digit, a Bombalı Sayılar-specific affordance) onto a differently-shaped game. Add real per-game theming here only if asked.
- Tapping an already-**matched** card (not during active flip/resolve play) doesn't call `flipCard` — `MemoryGameScreen`'s `onTap` branches on `card.isMatched` and calls `MemoryMatchController.pronounce(index)` instead, which speaks `card.label` in `card.languageCode` ('tr-TR' or 'en-US', set per-card in `startGame`) via `services/speech_service.dart`'s `SpeechService` (wraps the `flutter_tts` plugin, which uses the browser's Web Speech API on web — no audio assets needed). `pronounce` never mutates game state, purely a pronunciation-practice affordance (small `Icons.volume_up` hint shown on matched cards in `memory_card_widget.dart`). Since a real distinct "child voice" TTS voice isn't reliably available across browsers/OSes, `SpeechService` approximates a child-friendly tone with a higher pitch (1.4) and slower rate (0.42) rather than trying to select a named voice — document this reasoning if you touch it, so nobody "fixes" it into picking a voice by name and reintroduces cross-platform flakiness.

### Screen flow / rules (Renk mi Kelime mi? — Stroop test)

`games/stroop_game.dart`'s `StroopGame` wraps a single `ChangeNotifierProvider<StroopController>` around `_StroopRoot`, which switches on `StroopController.phase` (`StroopGamePhase`: `setup → playing → turnTransition → finished`, same four-phase shape as Bombalı Sayılar, unlike Kart Eşleştirme) to show `StroopSetupScreen` / `StroopGameScreen` / `StroopTurnTransitionScreen` / `StroopResultsScreen`.

- Classic Stroop interference test: each trial (`models/stroop_trial.dart`) shows a color *name* (`word`) rendered in an independently-random ink `StroopColor` (`models/stroop_color.dart`, 6 colors) — the correct answer is always the **ink** color, not the word. Response buttons deliberately show the color's *name* in neutral black text (`_ColorNameButton` in `stroop_game_screen.dart`), **not** a colored swatch: a colored circle would let the player match hue-to-hue without ever naming the color, defeating the point of the exercise — reading the ink and picking its *word* is what forces genuine naming. The button label itself stays neutral-colored so it doesn't introduce a second, unwanted Stroop conflict. `StroopTrial.options` (a shuffled `List<StroopColor>`, generated once per trial in `_generateTrial()`) fixes the button order for that trial — this must **not** be reshuffled inside the screen's `build()`, both because a rebuild happens mid-trial (e.g. when the correct/incorrect flash fires) and would visibly reshuffle the buttons out from under the player, and because a fixed per-trial order that's freshly randomized every trial (rather than a static order) is what prevents the player from learning button *position* instead of reading the word.
- Each player answers `roundsPerPlayer` (10, see `controllers/stroop_controller.dart`) trials before handing off; `StroopController.answer` is the only mutator during play — it records `correctCount`/`roundsPlayed`, shows a 350ms green/red feedback flash (`lastAnswerCorrect`) on the stimulus, then either generates the next trial or — once a player hits `roundsPerPlayer` — hands off via `_findNextUnfinishedPlayerIndex` (same pattern as `GameController` in Bombalı Sayılar) or finishes the game. The 350ms delay is guarded by the same `_generation`-counter pattern as the other two games' delayed callbacks, for the same reason (a restarted game can't be corrupted by a stale callback).
- Winner = most `correctCount` (`StroopController.rankedByCorrect`).
- No `AppThemeController`/`SoundService`/`SpeechService` integration here either — same reasoning as Kart Eşleştirme (a mismatched preset UI, or audio that doesn't fit a rapid-fire reaction test). Add only if asked.

### Screen flow / rules (Dizi Hafızası — sequence memory / "Simon")

`games/sequence_memory_game.dart`'s `SequenceMemoryGame` wraps a single `ChangeNotifierProvider<SequenceMemoryController>` around `_SequenceMemoryRoot`, which switches on `SequenceMemoryController.phase` (`SequenceMemoryGamePhase`: `setup → playing → turnTransition → finished`, same four-phase shape as Stroop, since the next player shouldn't see how far the previous one got) to show `SequenceMemorySetupScreen` / `SequenceMemoryGameScreen` / `SequenceMemoryTurnTransitionScreen` / `SequenceMemoryResultsScreen`.

- Each player gets exactly **one run**, not a fixed number of rounds: `SequenceMemoryController` auto-plays a growing `sequence` of `models/sequence_tile_color.dart` `SequenceTileColor`s (4 colors, 2×2 grid in `SequenceMemoryGameScreen`), then the player must tap them back in order via `tapTile`. A fully-correct repeat appends one more random tile and replays the (now longer) sequence; a wrong tap ends the player's turn immediately — their score (`SequenceMemoryPlayerState.bestLength`) is the sequence length they'd already completed, not the failed attempt's length. Reaching `maxSequenceLength` (20) without a mistake also ends the run, at the max score, so a run can't grow forever.
- Turn hand-off uses a boolean-`finished` `_findNextUnfinishedPlayerIndex`, the same shape as `GameController`'s (Bombalı Sayılar) rather than Stroop's `roundsPlayed`-counter version — appropriate here because each player's "amount of play" is a variable-length single run, not a fixed round count.
- The auto-playback (`_playSequence`) and the post-correct-repeat pause before replaying are both guarded by the same `_generation`/`_resolving` pattern as Stroop's delayed feedback and Kart Eşleştirme's flip-resolve delays — a stale timer from a restarted game can't corrupt the new one. `SequenceMemoryController.inputLocked` (`showingSequence || _resolving`) is exposed so `SequenceMemoryGameScreen` can disable tile taps during both playback and resolution.
- Winner = highest `bestLength` (`SequenceMemoryController.rankedByBestLength`).
- Feedback is intentionally asymmetric: a wrong tap flashes the tapped tile red (`wrongTile`), but there's no separate "correct" flash — the sequence visibly growing and replaying is itself the positive feedback, so a redundant success flash was left out.
- No `AppThemeController`/`SoundService`/`SpeechService`/`GameResultRepository` integration — same reasoning as Stroop/Kart Eşleştirme (mismatched preset UI / audio that doesn't fit the game / no persistence outside Bombalı Sayılar). Add only if asked.

### Screen flow / rules (Diziler — IQ-test style number pattern completion)

`games/pattern_game.dart`'s `PatternGame` wraps a single `ChangeNotifierProvider<PatternController>` around `_PatternRoot`, which switches on `PatternController.phase` (`PatternGamePhase`: `setup → playing → turnTransition → finished`, the same round-counted four-phase shape as Stroop, not the single-run shape of Dizi Hafızası) to show `PatternSetupScreen` / `PatternGameScreen` / `PatternTurnTransitionScreen` / `PatternResultsScreen`. The display name is "Diziler" (Turkish for "sequences") — the game's class/file names all keep the English `Pattern*` prefix from before the rename, same "Turkish vitrine, English identifiers" split every other game on the platform already has (`Dizi Hafızası` ↔ `SequenceMemory*`, `Renk mi Kelime mi?` ↔ `Stroop*`); `patternRoundsPerPlayer` in particular **must** stay that exact name, see the naming note below.

- Each trial (`models/pattern_trial.dart`'s `PatternTrial`) shows the first 4 terms of a 5-term number sequence plus a "?"; the player picks the hidden 5th term from 4 shuffled options.
- **`models/pattern_difficulty.dart`'s `PatternDifficulty`** (Kolay/Orta/Zor) is the second thing the setup screen asks for, alongside player count — chosen via `PatternDifficultySelector` (`widgets/pattern_difficulty_selector.dart`, a `SegmentedButton` copied from `MultiplicationDifficultySelector`'s shape) and passed into `PatternController.startGame(names, {required difficulty})`. Unlike `MultiplicationDifficulty` (which only scales numeric ceilings), the three levels here use **qualitatively different rule sets**, so `PatternController._generateTrial()` dispatches to three separate private generators (`_generateKolayTerms`/`_generateOrtaTerms`/`_generateZorTerms`) rather than parameterizing one formula:
  - **Kolay** reinforces multiplication tables: every sequence is five consecutive multiples of a single step 2–9 (e.g. `7, 14, 21, 28, ?` → the 7-times table; `42, 49, 56, ?` → still the 7-times table, just starting further in). This is a deliberate cross-game callback to Çarpım Bahçesi's tables, and the setup screen's visible `Text('Zorluk: ${_difficulty.hint}')` line says so explicitly (not a tooltip — tooltips don't discover well on touch, and the whole point is the parent/child sees why Kolay is worth picking).
  - **Orta is byte-for-byte the pre-difficulty behavior**: the original single-tier `_generateTrial` body (arithmetic ascending `start` 1–20/`step` 1–5, arithmetic descending `start` 25–50/`step` -1..-5, or geometric `start` 1–4/`ratio` 2–3, each branch 50/50) was moved into `_generateOrtaTerms()` unchanged. Making Orta the middle option means nobody who liked the old game sees different numbers by default.
  - **Zor** widens the same two rule types (`start` 1–40/`step` 2–9 ascending, `start` 60–120/`step` -2..-9 descending — the descending floor of 60 keeps the minimum term `60 - 4×9 = 24` safely positive) and adds a fourth branch: **descending geometric**, i.e. a dividing sequence (`1280, 320, 80, 20, ?` → 5, dividing by 4 each step). This is generated by building the normal ascending geometric list (`start` 1–6, `ratio` 2–4) and calling `.reversed.toList()` on it when the coin flip picks descending — reusing the ascending generator's positivity/integer guarantees rather than writing a second, division-based generator from scratch.
  - All terms are kept strictly positive by construction in every branch — no negative numbers are ever shown, and the correct answer can never be negative.
- **`spacing` (used to scale distractor magnitude) is computed generically now**: `(shown[1] - shown[0]).abs()`, straight off the two terms actually on screen, rather than each generator separately returning a `step`/`ratio`-derived value. This is direction-agnostic (works the same for the new descending-geometric branch as for ascending arithmetic) and is provably identical to the old per-branch computation for Orta.
- Wrong options are generated by offsetting the correct answer by a random magnitude scaled to `spacing`, rejecting any candidate that's non-positive, equal to the answer, or **equal to one of the 4 already-displayed sequence terms** (otherwise a trial like "1, 2, 3, 4, ?" could offer "4" — a number already visible on screen — as a wrong choice). `spacing` is never 0 in any branch, so the candidate pool is always wide enough that this loop terminates quickly.
- Each player answers `patternRoundsPerPlayer` (8, see `controllers/pattern_controller.dart`) trials before handing off; `PatternController.answer` is the only mutator during play, structured identically to `StroopController.answer` (350ms green/red feedback flash via `lastAnswerCorrect`, `_generation`-guarded delay, hand-off via `_findNextUnfinishedPlayerIndex`'s round-count variant once `roundsPlayed` hits the cap).
- **Naming note**: the round-count constant is `patternRoundsPerPlayer`, not `roundsPerPlayer` — Stroop's controller already declares a top-level public `roundsPerPlayer`, and `test/widget_test.dart` imports both controllers into the same file, so reusing that name would be an "ambiguous import" compile error. Any future trial/round-based game must pick its own distinctly-named top-level round-count constant for the same reason.
- `PatternController` takes an injectable `Random` (`PatternController({Random? random})`), the same pattern as `MultiplicationController`/`ChessAI`, added specifically so difficulty-tier tests can pin a seed and assert on the shape of generated sequences without flaking.
- Winner = most `correctCount` (`PatternController.rankedByCorrect`).
- `PatternGameScreen` builds two small private widgets inline (not extracted to `lib/widgets/`, matching Stroop's own inline `_ColorNameButton` precedent rather than the shared-widget-file precedent used by more complex/reused visuals like `grid_cell.dart`): `_NumberChip` (non-interactive, displays one sequence term or "?") and `_OptionButton` (`key: ValueKey(option)` for testability, mirroring Stroop's `_ColorNameButton(key: ValueKey(option))`).
- No `AppThemeController`/`SoundService`/`SpeechService`/`GameResultRepository` integration — same reasoning as Stroop/Kart Eşleştirme/Dizi Hafızası. Add only if asked.

### Screen flow / rules (Tepki Süresi — reaction-time test)

`games/reflex_game.dart`'s `ReflexGame` wraps a single `ChangeNotifierProvider<ReflexController>` around `_ReflexRoot`, which switches on `ReflexController.phase` (`ReflexGamePhase`: `setup → playing → turnTransition → finished`, the same round-counted four-phase shape as Stroop/Diziler) to show `ReflexSetupScreen` / `ReflexGameScreen` / `ReflexTurnTransitionScreen` / `ReflexResultsScreen`.

- This is the first game whose controller measures **elapsed wall-clock time** rather than just sequencing discrete choices. Each of `reflexRoundsPerPlayer` (5) rounds: a big tappable area (`ReflexGameScreen`'s `Key('reflexTapArea')` `GestureDetector`) shows "Bekle..." (`ReflexRoundState.waiting`, red) for a random delay between `_minSignalDelay` (1200ms) and `_maxSignalDelay` (3500ms), then flips to "ŞİMDİ! Dokun!" (`ready`, green) and starts a `Stopwatch`. Tapping during `waiting` is a false start — it records the fixed `falseStartPenaltyMs` (1000ms) instead of a real time. Tapping during `ready` stops the stopwatch and records `elapsedMilliseconds`.
- **`Stopwatch`, not `DateTime.now().difference(...)`**: `Stopwatch` is monotonic (immune to clock adjustments/NTP sync mid-measurement); `DateTime.now()` elsewhere in this codebase (e.g. `GameController`) is only ever used to store a timestamp, never to measure a duration — this is a deliberately different tool for a deliberately different job. Follow this precedent if you add more timing-sensitive games.
- **`_beginRound`'s pending signal-reveal delay is guarded by two conditions, not just `_generation`**: `if (generation != _generation || roundState != ReflexRoundState.waiting) return;`. The extra `roundState` check is genuinely load-bearing here (unlike in other games where `_generation` alone suffices) — a false start happens *within the same generation* (the game hasn't restarted), so the already-scheduled "reveal" timer must recognize the round already resolved to `tooEarly` and not silently flip it back to `ready`. `tap()`'s own reentrancy guard stays simple (`if (_resolving) return;` only) since `roundState ∈ {tooEarly, result}` is only ever true while `_resolving` is also true — checking both would be redundant.
- **Round-count constant is `reflexRoundsPerPlayer`**, not `roundsPerPlayer`/`patternRoundsPerPlayer` — same "ambiguous import" reasoning as Diziler's naming note above; every trial/round-based game needs its own distinctly-named top-level round-count constant since `test/widget_test.dart` imports every controller into one file.
- **Testability caveat**: `Stopwatch`/`DateTime` are **not** virtualized by `tester.pump()` — pumping virtual time does not change what `Stopwatch.elapsedMilliseconds` reports, since only `Future.delayed`/`Timer` are faked by the test framework. Tests must only assert `roundState` transitions and counters (`roundsPlayed`, `reactionTimes.length`), never a specific millisecond value. Two determinism tricks make this testable anyway: tapping immediately after `startGame` (no pump at all) is *always* a false start, since `_minSignalDelay` is a hard 1200ms floor; pumping the full `_maxSignalDelay` (3500ms) *always* reaches `ready` regardless of the RNG draw, since `_rng.nextInt(range)` never returns the range's upper bound.
- Winner = lowest average reaction time (`ReflexController.rankedByAverage`, `ReflexPlayerState.averageMs`).
- No `AppThemeController`/`SoundService`/`SpeechService`/`GameResultRepository` integration — same reasoning as the other games without it. Add only if asked.

### Screen flow / rules (Simon Diyor ki — Simon Says style attention/impulse control)

`games/simon_game.dart`'s `SimonGame` wraps a single `ChangeNotifierProvider<SimonController>` around `_SimonRoot`, which switches on `SimonController.phase` (`SimonGamePhase`: `setup → playing → turnTransition → finished`) to show `SimonSetupScreen` / `SimonGameScreen` / `SimonTurnTransitionScreen` / `SimonResultsScreen`. This game is structurally a near-exact copy of Stroop's controller (`SimonController.respond` mirrors `StroopController.answer`: 350ms `lastAnswerCorrect` flash, `_generation`-guarded delay, `_findNextUnfinishedPlayerIndex` round-count hand-off) — by the time this was the third game built on this shape (after Stroop and Diziler), it didn't need a separate design-validation pass; only the trial content and the "pass" concept below are genuinely new.

- The board is 4 **fixed** color+shape combinations — `models/simon_tile_id.dart`'s `SimonTileId` enum (`redCircle`/`blueSquare`/`greenTriangle`/`yellowStar`), not a class with custom equality: since the board is always exactly these 4 pairings, an enum (same pattern as `StroopColor`/`SequenceTileColor`) is sufficient and gives free identity comparison for `respond()`. Each trial (`models/simon_trial.dart`'s `SimonTrial`) shuffles the 4 tiles' on-screen order (`boardOrder`) — same reasoning as Stroop's per-trial `options` shuffle: prevents the player from answering by memorized position instead of reading the instruction.
- `SimonTrial.instructionText` builds the Turkish instruction from a template that never appends a suffix directly onto the variable color/shape name (`"{ad} rengine dokun!"` / `"{ad} şekline dokun!"`), avoiding Turkish vowel-harmony suffix agreement entirely — the fixed word after the name carries the grammar, not the name itself. If you add more generated-Turkish-text games, follow this template trick rather than trying to conjugate a dynamic word.
- **The "Simon Says" twist**: each trial's `obey` (true ~70% of the time) determines whether the instruction is prefixed with `"Simon dedi ki: "`. `SimonController.respond(SimonTileId? tapped)` takes a **nullable** tile — `null` means the player tapped "Pas Geç" (`SimonGameScreen`'s `Key('simonPassButton')` button) instead of a tile. Correct response: `tapped == trial.target` when `obey`, `tapped == null` when not `obey`. This is deliberately a forced explicit choice (tile or Pas Geç) every round rather than a passive "do nothing within a time window" detection — simpler to implement and clearer for the platform's family/kid audience than adding Tepki Süresi-style timing logic here too.
- Round-count constant is `simonRoundsPerPlayer` (10, same tempo as Stroop) — not `roundsPerPlayer`/`patternRoundsPerPlayer`/`reflexRoundsPerPlayer`, same "ambiguous import" reasoning documented on the other games' round constants.
- Winner = most `correctCount` (`SimonController.rankedByCorrect`).
- Skill rating matches Stroop's exactly (`GameSkillRatings(zeka: 3, ingilizce: 0, iq: 2, hafiza: 1)`) since the two games test essentially the same attention/impulse-control profile.
- No `AppThemeController`/`SoundService`/`SpeechService`/`GameResultRepository` integration — same reasoning as the other games without it. Add only if asked.

### Screen flow / rules (Kayan Yapboz — classic 15-puzzle)

`games/puzzle_game.dart`'s `PuzzleGame` wraps a single `ChangeNotifierProvider<PuzzleController>` around `_PuzzleRoot`, which switches on `PuzzleController.phase` (`PuzzleGamePhase`: `setup → playing → turnTransition → finished`) to show `PuzzleSetupScreen` / `PuzzleGameScreen` / `PuzzleTurnTransitionScreen` / `PuzzleResultsScreen`. Unlike every trial/round-based game above, this one follows **Bombalı Sayılar's** shape instead: the same player keeps going until they finish (solve their board), not a fixed round count — `PuzzleController.moveTile` is a direct structural copy of `GameController.selectCell` (`controllers/game_controller.dart`), and it's the first controller since Bombalı Sayılar that needs **no** `_generation`/`_resolving` guard at all, because it's entirely synchronous — there's no `Future.delayed` anywhere in it (no feedback flash on a slide; the board itself is the only feedback needed).

- Board is 4×4 (`puzzleGridSize`, `models/puzzle_player_state.dart`), values `1..15` plus `0` for the empty cell; solved = `[1,2,...,15,0]` (`isPuzzleSolved`). Each player gets their own independently-shuffled board (`PuzzlePlayerState.generateShuffledTiles`), mirroring Bombalı Sayılar's per-player `bombLayout`.
- **Solvability**: a genuinely random permutation of a 15-puzzle is only solvable ~50% of the time (permutation parity constraint). Rather than implementing parity-checking, the board is shuffled by starting from the solved state and performing `_shuffleMoves` (150) random *legal* slides — since every step is the reverse of a real move, the result is always solvable by construction, no parity math needed. Reuse this technique for any future sliding-tile puzzle.
- `adjacentIndices(index)` (shared top-level helper, used by both the shuffler and `PuzzleController.moveTile`) returns the up/down/left/right neighbor positions. `moveTile(index)` is a no-op unless `index` is adjacent to the current empty cell — tapping a non-adjacent tile or the empty cell itself does nothing.
- Winner = fewest `moveCount` (`PuzzleController.rankedByMoves`), same "fewest wins" polarity as Bombalı Sayılar's `rankedByAttempts`.
- **Test-design note**: solving a real shuffled 15-puzzle in a test would require an actual solver. Tests instead directly set `controller.currentPlayer.tiles` to a one-move-from-solved state (the established "controller fields are public, tests may set them directly" convention from Diziler/Dizi Hafızası) and verify that the single correct move solves it and triggers hand-off — never exercise a fully-shuffled board end-to-end in a test.
- No `AppThemeController`/`SoundService`/`SpeechService`/`GameResultRepository` integration — same reasoning as the other games without it (note Bombalı Sayılar's use of these is specific to that game, not a "spatial/board game" category rule). Add only if asked.

### Screen flow / rules (Satranç — chess, vs. computer or local 2-player)

`games/chess_game.dart`'s `ChessGame` wraps a single `ChangeNotifierProvider<ChessController>` around `_ChessRoot`, which switches on `ChessController.phase` (`ChessGamePhase`: `setup → playing → finished` — **no** `turnTransition`) to show `ChessSetupScreen` / `ChessGameScreen` / `ChessResultsScreen`. This is the first game with a real rules engine and an AI opponent, and it's built from scratch (no pub.dev chess package).

- **Board representation**: `models/chess_board.dart`'s `ChessBoard` holds a flat `List<ChessPiece?> squares` of length 64 (`index = rank*8 + file`, see `models/chess_square.dart`'s `squareIndex`/`fileOf`/`rankOf` helpers), plus `sideToMove`, 4 castling-rights booleans, `enPassantTargetSquare`, `halfMoveClock`, `moveHistory`, and `positionSignatures` (for threefold repetition). A flat list over a 2D list matches the platform's existing precedent (`PuzzlePlayerState.tiles` is also a flat `List<int>`) and is trivial to clone.
- **The single biggest architectural decision**: `ChessBoard.applyMove(move)` returns a **new** `ChessBoard` — it never mutates `this`, and there is **no** `undoMove()` anywhere. A hand-rolled undo (correctly reversing castling rights, the en passant target, the half-move clock, and re-inserting a captured piece at the right square even for en passant) is the most bug-prone part of a hand-rolled chess engine; since the board is only 64 elements, cloning it is cheap enough (at the AI's shallow search depth, see below) to eliminate that entire bug category. Legal-move filtering (simulate → check king safety) and the AI's search both go through this one `applyMove` path — there is no separate "fast" mutate-in-place path for search.
- **`ChessBoard.custom({...})`** is a public factory (alongside `ChessBoard.initial()` and `ChessBoard.empty()`) that lets tests (or any future feature) construct an arbitrary position directly — every other `ChessBoard` field besides `squares` is `final`, so `ChessBoard.empty()` alone can't set castling rights/`sideToMove`/en passant target after the fact. Tests build positions this way and assign straight to `ChessController.board` (the same "controller fields are public, tests set them directly" convention as Puzzle's `controller.currentPlayer.tiles`).
- **`ChessGamePhase` has no `turnTransition`** — unlike every other multiplayer game on the platform. Those games hide *secret* per-player state during hand-off; chess has none (the board is always visible to both players), and moves happen far more often than e.g. Kayan Yapboz's once-per-solved-board transition, so a "pass the device" interstitial after every single move would badly disrupt the game's pace. The automatic board flip (below) already serves as the hand-off cue. This mirrors Kart Eşleştirme's `MemoryGamePhase` skipping `turnTransition` for the same reason.
- **Board orientation**: `ChessController.viewpointColor` is `board.sideToMove` in `ChessMode.twoPlayer` (flips every turn — the actual feature the user asked for: whoever's turn it is sees their own pieces at the bottom) but is pinned to `humanColor` for the whole game in `ChessMode.vsAi` (only one human is at the device, so flipping would be pointless motion). `boardFlipped = viewpointColor == PieceColor.black`. `ChessGameScreen`'s `_ChessBoardView` implements the flip by **reordering which square index is drawn in which grid cell** (a `displayOrder` list computed from `boardFlipped`), never `Transform.rotate` on the widget tree — rotating the whole board 180° would also flip every piece's Unicode glyph upside down.
- **AI** (`services/chess_ai.dart`, pure Dart, no Flutter import): negamax + alpha-beta pruning (the standard single-function form of minimax), material values + Michniewski-style piece-square tables, MVV-LVA move ordering for effective pruning, wrapped in **time-budgeted iterative deepening**. Runs fully synchronously — `dart:isolate`/`compute()` isn't reliable on Flutter web, so there's no threading escape hatch, and the search time *is* UI freeze time. That's what the budget is for: depths 1, 2, 3… are searched in turn and when `ChessDifficulty.timeBudgetMs` runs out the in-progress depth is abandoned and the **last completed depth's** best move is played. `_outOfTime` checks the clock once every 1024 nodes (checking every node measurably slowed the search).
- **Difficulty 1-5** (`models/chess_difficulty.dart`, `ChessDifficulty`) is the only thing that configures the AI, and it sets three knobs at once: `searchDepth`, `timeBudgetMs`, and `blunderChance`. The measured per-depth cost on the Dart VM (opening/middlegame) is ~15 ms / ~30 ms / ~230 ms / ~1.5 s / ~14 s for 1-5 plies, and dart2js is several times slower again — so **a level is not a depth**: levels 4-5 aim deep but are capped by the budget, and levels 1-2 additionally play a random legal move some of the time. That randomness is deliberate: even a 1-ply search never hangs a piece, so depth alone could not produce a beatable-by-a-beginner opponent. `ChessAI` takes an injectable `Random` so tests can make that deterministic.
- **Clock** (`models/chess_time_control.dart`: Süresiz / 5 / 10 / 30 dk). `ChessController` runs a `Timer.periodic(chessClockTick)` that **subtracts one tick** from the side to move rather than reading a `Stopwatch`/`DateTime` delta — those aren't virtualized by `tester.pump()` (same constraint documented for Tepki Süresi), so a tick-based counter is the only way the "flag falls" path is testable. Cost: a throttled background browser tab makes the clock run slow; accepted for this platform. Running out of time sets `ChessOutcomeReason.timeout` and hands the win to the opponent (the "opponent can't mate with what's left → draw" tournament exception is deliberately not implemented).
- **`startGame`'s `timeControl` defaults to `unlimited`, and so does the setup screen.** This is load-bearing for the test suite, not just a product preference: a running clock schedules a frame every second, so `pumpAndSettle()` on a timed game never settles and every existing chess widget test would hang. New tests that do use a clock must pump explicitly (`tester.pump(Duration(seconds: 3))`), never `pumpAndSettle`.
- **Evaluation bar** (`widgets/chess_evaluation_bar.dart`): the vertical bar left of the board fills white/black by `ChessController.whiteWinChance`, a logistic transform of `ChessAI.evaluateForWhite` (the same static evaluation the search uses at its leaves — no extra search, so it costs a 64-square loop per move). The bar **flips with the board** (`boardFlipped`), so whichever color is at the bottom of the board fills from the bottom. `evaluationCentipawns` is stored on the controller and refreshed only when a move lands, so the once-a-second clock rebuilds don't re-evaluate. Once the game is over the bar reads the real outcome instead of the static score.
- **Move history** (`models/chess_notation.dart` + `widgets/chess_move_history.dart`): notation is generated **at the moment the move is played** (`ChessController._applyAndRecord`, the single place a move is applied) and appended to `moveNotations`, because algebraic notation needs both the before-board (to know whether a second piece of the same type could also reach that square, i.e. the disambiguation suffix) and the after-board (check `+` / mate `#`). `board.moveHistory` keeps the raw moves; regenerating notation from it later would mean replaying the whole game. Piece letters are **Turkish** (Ş/V/K/F/A — `chessPieceLetters`), matching the rest of the app rather than international K/Q/R/B/N.
- `ChessMoveHistory` renders both layouts from the same move-pair data via an `axis` parameter: a vertical panel right of the board on wide screens, a horizontally scrolling strip under the board below `_BoardArea._sidePanelBreakpoint` (a phone has no room for a side panel, and shrinking the board to make one would hurt play). It auto-scrolls to the newest move with `jumpTo`, not `animateTo` — a running animation would needlessly stretch `pumpAndSettle` in tests.
- `_BoardArea` in `chess_game_screen.dart` computes the board's side length once from the incoming constraints and hands it to the bar, the board and the history panel — an `AspectRatio` alone couldn't tell the neighbors how tall to be.
- **`ChessController._makeAiMove`** wraps the AI's move in the same `_generation`-guarded-delay pattern as every other controller's async feedback (Simon/Stroop's flash, etc.): a short `Future.delayed(150ms)` lets a "Bilgisayar düşünüyor..." frame actually paint before the (blocking) synchronous search runs, and `_generation` is checked both after the delay and after the search completes — `restart()` bumps `_generation`, so a stale AI move computed against an old game can never apply itself to a game that was restarted while it was "thinking."
- **Interaction model**: `ChessController.selectSquare(int square)` (two-tap pick-up/put-down, not `attemptMove(from, to)`) — matches the platform's one-argument-per-cell `onTap` convention (`moveTile(index)`, `flipCard(index)`, `tapTile(index)`) and naturally holds `selectedSquare`/`selectedSquareLegalMoves` for legal-destination-dot highlighting.
- **Promotion**: `ChessBoard`'s move generator produces **4 separate `ChessMove`s** (queen/rook/bishop/knight) whenever a pawn move lands on the back rank, all sharing the same `from`/`to`. When `selectSquare`'s second tap matches more than one legal move, that's exactly the promotion case — it populates `pendingPromotionMoves` instead of committing, and `ChessGameScreen` (the one `StatefulWidget` chess screen, tracking a local `_promotionDialogShown` flag purely as presentation state) shows an `AlertDialog` with the 4 glyph choices; `ChessController.resolvePromotion(type)` commits the chosen one. Auto-queen was considered and rejected — a real choice is correct chess and the extra dialog is cheap.
- **Castling** tracks 4 rights booleans, cleared on king move, on rook move from its home square, **and when a rook is captured on its home square even if it never moved** (an easy edge case to miss). Castling's legality additionally checks that the king's transit square isn't attacked (`ChessBoard._canCastleKingside`/`_canCastleQueenside`) — the generic "simulate the move, check king safety" filter alone only covers the *landing* square, not the square the king passes through.
- **Draw rules included** (cheap at 64 squares, so no reason to skip them): 50-move rule (`halfMoveClock`), threefold repetition (`positionSignatures`, one string per position reached), and basic insufficient material (K-vs-K, K+single-minor-vs-K). Same-color-bishop-vs-bishop insufficient material is deliberately **not** detected — a rare edge case, and skipping it is safe in the "wrong" direction (the game just continues to a real conclusion instead of auto-drawing early).
- **Outcome model**: no `rankedByX` getter (unlike every other game) — a win/loss/draw isn't a numeric per-player score. `ChessController.outcome` (`ChessOutcome`: `whiteWins`/`blackWins`/`draw`) + `outcomeReason` (`ChessOutcomeReason`: `checkmate`/`stalemate`/`fiftyMoveRule`/`repetition`/`insufficientMaterial`) are set directly by `_checkGameEnd()` and read by `ChessResultsScreen`, which also doesn't use the platform's usual `ranked.length == 1` solo-headline pattern — 1-player chess means "vs. AI," not "no opponent," so it branches on `mode == ChessMode.vsAi` instead.
- No `AppThemeController`/`SoundService`/`SpeechService`/`GameResultRepository` integration — same "add only if asked" reasoning as every other non-Bombalı-Sayılar game. `widgets/chess_square_widget.dart`'s light/dark square colors are hardcoded for the same reason as Kart Eşleştirme's fixed card-back color.
- **Pieces are drawn, not typed.** `widgets/chess_piece_glyph.dart`'s `ChessPieceGlyph` paints `ChessPiece.solidGlyph` twice — a stroked outline under a filled glyph — so a white piece is genuinely white-filled. Unicode's white piece symbols (♔♕♖…) are hollow outlines: rendered as plain text they let the square color show through and read as "transparent" pieces on the board, which is what this replaces. Both colors therefore use the *solid* (black) glyph set and differ only in fill/outline color. `ChessPiece.glyph` still returns the true per-color symbol, but nothing on the board uses it any more.
- **Piece size is a ratio of the square, never a fixed `fontSize`.** `ChessSquareWidget` reads its own side length from a `LayoutBuilder` and passes `size * _pieceScale` down; with `height: 1.0` + `TextLeadingDistribution.even` the text box is exactly that tall, so `_pieceScale = 1.0` fills the square without clipping. Don't go back to a constant font size — the board scales with the window, so a constant looks correct at exactly one board size and tiny at every other.
- **Because pieces are no longer `Text`, tests can't use `find.text('♙')`.** `test/widget_test.dart`'s `_findPiece(type, color)` helper matches on `ChessPieceGlyph.piece` via `find.byWidgetPredicate` instead (that field is public for exactly this reason), and the promotion dialog's four choices carry `ValueKey('promote_<type>')` keys for the same reason.
- The board additionally highlights the **last move** (both squares) and the **checked king** (red radial), and prints file letters along the bottom row / rank numbers down the left column. All three are computed in `_ChessBoardView` from `displayOrder`, so they follow the board when it flips in two-player mode — never hardcode a1 at the bottom-left.
- **Performance, now bounded by the budget rather than by depth**: every visited search node runs a full `legalMoves()` (generation + per-candidate clone-and-king-safety-check), which is far more expensive per node than a bare leaf evaluation — this is why raw depth scales so badly (see the measured numbers above). The time budget is what keeps that from reaching the user as a multi-second freeze; if the AI still feels laggy on a real web release build, lower the budgets in `ChessDifficulty` before touching the engine (a cheaper king-safety pre-filter is the next lever, and would speed up every level at once).

### Screen flow / rules (Çarpım Bahçesi — teaching multiplication via the array model)

`games/multiplication_game.dart`'s `MultiplicationGame` wraps a single `ChangeNotifierProvider<MultiplicationController>` around `_MultiplicationRoot`, which switches on `MultiplicationController.phase` (`MultiplicationGamePhase`: `setup → playing → turnTransition → finished`, the round-counted four-phase shape) to show `MultiplicationSetupScreen` / `MultiplicationGameScreen` / `MultiplicationTurnTransitionScreen` / `MultiplicationResultsScreen`. This is the platform's first **arithmetic-teaching** game: the goal is not to drill "7 × 8 = ?" from memory but to show what multiplication *means*.

- **Everything is built on the array (dizi) model**: a multiplication is a rectangle of objects, and `3 × 4` means "3 rows of 4" = `4 + 4 + 4`. That's why `models/multiplication_trial.dart`'s `MultiplicationTrial` is defined by `rows`/`columns` (+ a `context`, see below) and `answer` is *derived* (`rows * columns`), rather than the trial storing a target number. `repeatedAdditionText` ("3 × 4 = 4 + 4 + 4 = 12") and `runningTotals` (4, 8, 12) fall out of the same two fields. `repeatedAdditionText` switches to a compact form (`4 + 4 + … (10 kere) = 40`) above `_maxExpandedRows` (6) — otherwise a 12-row trial produces a line no screen can hold.
- **Two trial kinds, strictly alternating** (`MultiplicationTrialKind`): odd rounds are `array` (a finished grid is shown, the player picks the total from 4 options — *read* the model), even rounds are `build` (a multiplication is stated, the player constructs the grid with `+`/`-` steppers — *apply* the model). The alternation is deliberate rather than random so every player gets four of each, and so tests can rely on round 1 being `array`.
- **The explanation panel is the actual product**, not the score. After *every* answer — right or wrong — `showingExplanation` goes true and the round **does not advance**: the target grid is redrawn with `showRunningTotals`, each row's cumulative total fading in via a 600 ms `TweenAnimationBuilder`, above `groupingText` and `repeatedAdditionText`. Only "Devam" (`Key('multiplicationContinue')` → `continueAfterExplanation()`) moves on.
- **Consequence: this controller contains no `Future.delayed` at all**, and therefore needs neither the `_generation` counter nor the `_resolving` flag that guard Stroop's / Diziler's / Simon's 350 ms feedback flash — there is no pending callback that a restart could corrupt. It is fully synchronous, like `PuzzleController`. **Do not "modernize" it into a timed flash**: reading the explanation takes time, and a timer would take that time away from the child. If you ever do add a delayed callback here, you must add the `_generation` guard with it.
- **Commutativity counts as correct, on purpose.** In a `build` round, target `3 × 4` with a `4 × 3` grid sets `lastAnswerCommuted` and scores as **correct**; the panel then teaches the property ("… aynı sonucu verir … sıranın değişmesi sonucu değiştirmez"). Marking a mathematically equal answer wrong would be both unfair and a wasted lesson.
- **Distractors are pedagogical, not random** (`_generateOptions`): `answer ± columns` (miscounted a row), `answer ± rows` (missed a column), `rows + columns` (added instead of multiplying — the classic error), `answer ± 1`. Because both factors are ≥ 2, at least three positive candidates distinct from the answer always exist, so no top-up loop is needed.
- **Every trial happens in a real-life scene** (`models/multiplication_context.dart`'s `MultiplicationContext`, ~30 of them in the top-level `const multiplicationContexts` list). A scene supplies the cell emoji, an optional `groupEmoji`/`columnHeaderEmoji` for the grid's side strips, an optional `unit` (" TL"/" gün"/" m²"), an optional `fixedColumns`, and — the bulk of it — the Turkish sentences. The point is that a bike's wheels, an egg carton, a week's days and an outfit-combination are *the same rectangle*; the scene changes, the math doesn't.
  - **The sentences are hand-written per scene, with only `{r}`/`{c}`/`{n}` substituted in.** This is the `SimonTrial.instructionText` vowel-harmony decision taken one step further: rather than trying to conjugate a variable noun ("koli" → "kolide"), the whole sentence is authored for the scene and code only drops digits into it. Never introduce a generic sentence builder here that appends a suffix to a scene noun.
  - **`MultiplicationContextKind`** (`dizi` / `esitGrup` / `para` / `zaman` / `alan` / `kombinasyon` / `karsilastirma`) is *only* used for text framing and which side strips are drawn — every kind still renders through the same `MultiplicationArrayView` and the same `rows * columns`. There is deliberately no per-kind visualisation branch.
  - **`fixedColumns`** encodes a count that comes from the world, not the RNG (a bike has 2 wheels, a spider 8 legs, a week 7 days). `_generateTrial` then randomises only `rows`. A scene whose `fixedColumns` exceeds the round's factor ceiling is filtered out — which is exactly why the 8-legged spider never appears on Kolay, and never in an Orta *build* round (`buildMaxFactor` 6).
  - **`buildPrompt == null` means "reading rounds only"** (`isBuildable`). Money, time and multiplicative-comparison scenes have no build prompt, because "now build 3 weeks yourself" is a contrived instruction. `_pickContext` enforces this, and the screen's `trial.buildPrompt ?? '<r> × <c> kur!'` fallback is only a safety net.
  - **Scene pools are the second thing difficulty selects**, alongside the factor ceilings — see `levels` on each scene. Kolay = countable, tangible, mostly fixed-column equal groups; Orta = bigger arrays plus the first abstractions (money, time); Zor = area model, Cartesian combination, multiplicative comparison, i.e. the cases where multiplication stops being "repeated addition of visible objects".
  - **`_pickContext` weights scenes introduced at the current level twice** (`MultiplicationContext.introducedAt`). Without it, carried-over lower-level scenes outnumber the new ones and an 8-round game on Zor could easily show none of the area/combination scenes that define the level. On Kolay every scene is new, so the weighting is a no-op there.
- **Difficulty carries two factor ceilings, not one** (`models/multiplication_difficulty.dart`): `arrayMaxFactor` (5/10/12) and `buildMaxFactor` (4/6/8). Reading rounds can render a 12 × 12 grid freely because `MultiplicationArrayView` shrinks the cells; building rounds can't, because every row/column there costs a tap. `minFactor` is 2 platform-wide (a `1 × n` strip teaches nothing about rectangles). Chosen on the setup screen via `widgets/multiplication_difficulty_selector.dart`, and passed as `startGame(names, {required difficulty})` — the same named-argument shape as `MemoryMatchController.startGame(names, {required category})`.
- **`MultiplicationArrayView`'s two side strips** (`rowLeadingEmoji` down the left, `columnHeaderEmoji` across the top) are what let one grid widget express all seven scene kinds: an equal-groups row is labelled with the group itself (🚲 → 🛞 🛞), a combination grid is labelled on both axes (👕 × 👖). They are drawn borderless (`_LabelCell`, not `_ArrayCell`) precisely so they are not counted as objects, and each occupies a virtual extra column/row in the cell-size math — forget that and the grid overflows once a strip is added.
- **`widgets/multiplication_array_view.dart` lives in `lib/widgets/` (not inline in the screen) because it is genuinely used three times**: as the question in a reading round, as the player's live construction in a building round, and as the lesson in the explanation panel. Cell size comes from a `LayoutBuilder` and is clamped to `[14, 44]`, the same technique as `widgets/number_grid.dart`; a `FittedBox(fit: BoxFit.scaleDown)` sits under it purely as a last-resort net for the case where even the clamped minimum can't fit (12 × 12 on a very narrow phone) — overflow is a hard failure in debug, shrinking is not. A regression test pins that worst case at 320 × 560.
- Round-count constant is `multiplicationRoundsPerPlayer` (8) — own name, same "ambiguous import" reasoning as every other game's round constant.
- Winner = most `correctCount` (`rankedByCorrect`).
- **Test note**: three data-level tests guard the scene table without pinning any individual sentence — every difficulty must have at least one usable reading *and* building scene, no template may leave a `{` unsubstituted (and every `conclusion` must contain `{n}`), and a full 8-round generated game per difficulty must only ever produce scenes from that level, within that level's ceiling, with `fixedColumns` respected. Add scenes freely; those tests are what catch a scene that can never actually be selected.
- **Test note**: `_answerMultiplicationCorrectly` answers a `build` round by assigning `controller.buildRows`/`buildColumns` directly rather than tapping the steppers up to 8 times each (the established "controller fields are public, tests may set them directly" convention from Kayan Yapboz). The commutativity test likewise *assigns* a fixed non-square `currentTrial` — a randomly generated square trial (3 × 3) would make "flip it" identical to the target and the test meaningless.
- No `AppThemeController`/`SoundService`/`SpeechService`/`GameResultRepository` integration — same "add only if asked" reasoning as every other non-Bombalı-Sayılar game.

### Player count (1 or 2 players — platform-wide convention)

Every game's setup screen offers `widgets/player_count_selector.dart`'s `PlayerCountSelector` (a `SegmentedButton<int>`, "1 Kişi" / "2 Kişi", default 2). Selecting 1 hides the second name field and `startGame` is called with a one-element names list — nothing else needs to special-case solo play:

- Both `GameController` and `MemoryMatchController` were already generic over `List<PlayerState>`/`List<MemoryPlayerState>`, so a 1-player list "just works": `_findNextUnfinishedPlayerIndex` (Bombalı Sayılar) finds no other player and goes straight to `finished` (so `TurnTransitionScreen` is simply never reached), and `MemoryMatchController`'s `currentPlayerIndex = (currentPlayerIndex + 1) % players.length` on a mismatch is a no-op with `players.length == 1`.
- The only per-game adjustments needed are **wording**, not logic: each results screen computes a `headline` that says `'Tebrikler, ${winner.name}!'` when `ranked.length == 1` instead of the 2-player `'${winner.name} kazandı!'` / `'Berabere!'` phrasing (comparing yourself to a nonexistent opponent reads oddly). `MemoryGameScreen` similarly switches its `AppBar` title from `'Sıra: ${current.name}'` to `'${current.name} oynuyor'` (matching `GameScreen`'s own convention) when solo, since there's no "turn" to announce.
- When adding a new game, replicate this: build `PlayerCountSelector` + conditional second field into its setup screen, and give its results screen the same `ranked.length == 1` solo-headline branch.

### Kimlik doğrulama (`AuthController` / `AuthGate` / `LoginScreen`)

`ProfileController`'dan tamamen ayrı bir katman: gerçek bir oturum açma zorunluluğu. `controllers/auth_controller.dart`'ın `AuthController`'ı Supabase Auth'un **Google OAuth** sağlayıcısını sarar; `screens/auth_gate.dart`'ın `AuthGate`'i `main.dart`'ta artık `GameCatalogScreen.routeName` ('/') rotasının ürettiği asıl widget'tır — `AuthController.isSignedIn` false iken `screens/login_screen.dart`'ın `LoginScreen`'ini ("Google ile Bağlan" butonu), true iken `GameCatalogScreen`'i gösterir.

- **Neden iki ayrı sistem**: bir Gmail hesabıyla giriş yapan kişi (örn. ebeveyn) ekranda kendi ismini değil çocuğunun ismini görmek isteyebilir — o yüzden "kimsin" (`AuthController`, gerçek kimlik doğrulama) ile "oyunlarda hangi isimle görünürsün" (`ProfileController`, cihaz-yerel tercih) kasıtlı olarak birbirinden bağımsız. `signOut()` `ProfileController`'a dokunmaz.
- **`isSignedIn` neden `bool`, gerçek bir `Session` değil**: testlerin (`GamePlatformApp(authController: AuthController()..isSignedIn = false)` gibi) gerçek bir Supabase `Session`/`User` nesnesi kurmadan giriş/çıkış durumunu simüle edebilmesi için — bkz. Puzzle'ın "controller alanları public, testler doğrudan set edebilir" konvansiyonuyla aynı yaklaşım.
- **`signOut()` bilerek senkron**: `isSignedIn`'i anında false'a çekip dinleyicilere bildirir, Supabase'e oturumu kapatma isteğini ise `unawaited(...)` ile arka planda, sonucunu beklemeden gönderir (`SignOutScope.local`, ağ çağrısı gerektirmez). Bunun nedeni bir hata: ilk halde `Future<void> signOut() async { await ...signOut(...); isSignedIn = false; ... }` yazılmıştı ve bu, testte `pumpAndSettle()`'ın (var olmayan `test.supabase.co` sunucusuna gidip dönmeyi bekleyen, dolayısıyla hiç frame planlamayan) bir `Future`'ı beklememesi yüzünden çıkışın hiç gerçekleşmemiş gibi görünmesine yol açtı — çıkış her zaman anında ve ağdan bağımsız olmalı (bkz. `SoundService`/`SpeechService`'teki "yan servis asla oyunu bozmasın" deseniyle aynı tercih), bunu değiştirirsen aynı tuzağa düşmemek için `signOut`'u tekrar ağ çağrısını bekler hale getirme.
- **Testteki varsayılan tam tersi yönde**: `ProfileController`'ın aksine (varsayılan = boş/yüklenmemiş), `AuthController`'ın test varsayılanı **oturum açılmış** (`AuthController()..isSignedIn = true`) — çünkü mevcut ~45 testin tamamı doğrudan oyun ekranlarını test ediyor, giriş ekranıyla hiç uğraşmamaları gerekiyor. Sadece giriş/çıkış davranışını test eden birkaç test `authController`'ı açıkça verir.
- **Google OAuth sağlayıcısı Supabase'de manuel kurulum gerektirir** — bu depodaki kod tarafı tamamen hazır, ama çalışması için Supabase Dashboard'da (Authentication → Sign In / Providers → Google) bir Google Cloud OAuth istemci kimliği/sırrı girilmesi lazım; bu adım koddan yapılamaz ve bir sır (Client Secret) içerdiği için Claude tarafından da girilmemelidir — kullanıcı kendisi yapmalı.
- **Tek bir Google Cloud OAuth client, birden fazla Supabase projesiyle paylaşılıyor**: OAuth client Google Cloud projesi `oyun-platformu-506422`'de yaşıyor (proje adına rağmen bu client Supabase projesinden bağımsız — Google tarafında "kim login olabilir" tanımlıyor, Supabase tarafında "hangi proje bu client'ı kullanıyor" ayrı bir eşleştirme). Supabase projesi değiştirildiğinde (bkz. "Deployment" altındaki not ve `config/supabase_config.dart`), bu client'ın **Authorized redirect URIs**'ine yeni projenin `https://<proje-ref>.supabase.co/auth/v1/callback` adresi eklenmeli (eskisini silmeye gerek yok, birden fazla redirect URI aynı anda geçerli kalabilir) ve aynı Client ID/Secret yeni Supabase projesinin Google provider ayarına girilmeli — yeni bir Google OAuth client oluşturmaya gerek yok.
- **`MaterialApp.debugShowCheckedModeBanner: false`**: debug modundaki köşe "DEBUG" şeridi bilerek kapatıldı; kaldırılmasının nedeni salt kozmetik (kullanıcı isteği), fonksiyonel bir yan etkisi yok — geri açmak istersen bu satırı silmen yeterli.

### Game rules (Bombalı Sayılar — must stay consistent when touching game logic)

- Grid is 5 columns × 10 rows, numbers 1–50 (`row * colCount + col + 1`, see `models/player_state.dart`).
- Each player gets their own random bomb layout at game start (`PlayerState.generateBombLayout`): 2 bomb columns per row, **fixed for that player's entire game** — this is deliberate (the game is a memory exercise: hitting a bomb resets progress but not the layout, so players must remember prior attempts).
- Turn logic lives in `GameController.selectCell`: a bomb hit resets `currentRow` to 0 and increments `attempts`, but does **not** pass the turn to the other player — the same player keeps retrying. The turn only passes once a player clears all 10 rows in one unbroken run (`_findNextUnfinishedPlayerIndex`). Winner = fewest `attempts` (`GameController.rankedByAttempts`).
- `PlayerState.streakClearedCols` tracks only the *current* run's cleared cells and is wiped on a bomb hit — the UI must never leak information about a previous run's safe cells, since remembering them is the point of the game.

### Repository abstraction (Supabase — wired up for Bombalı Sayılar)

`data/game_result_repository.dart` defines `GameResultRepository` (`saveResult`/`fetchResults`). `data/in_memory_game_result_repository.dart` (session-scoped, no persistence) was the only implementation until Supabase was connected; `data/supabase_game_result_repository.dart` (`SupabaseGameResultRepository`) is now the one actually wired into `GameController` in `games/bombali_sayilar_game.dart` — it reads/writes the `public.game_results` table (schema + RLS policies in `supabase/schema.sql`, run once via the Supabase SQL editor) through `Supabase.instance.client`. `InMemoryGameResultRepository` is kept around only as a lightweight alternative for tests/local experiments that want to avoid a network dependency, not because Supabase is still deferred.

- **Project config**: `lib/config/supabase_config.dart` hardcodes the project `url` and the anon/publishable key. This is intentional, not an oversight — the Supabase anon key is designed to be public in client bundles (per Supabase's own docs); real access control is the RLS policies in `supabase/schema.sql`, not secrecy of this key.
- **Init timing**: `main()` is `Future<void>` and calls `WidgetsFlutterBinding.ensureInitialized()` + `await Supabase.initialize(url: ..., publishableKey: ...)` before `runApp`. `SupabaseGameResultRepository`'s constructor reads `Supabase.instance.client` eagerly, so anything that constructs one (like `BombaliSayilarGame`'s `MultiProvider`) requires `Supabase.initialize` to have already run in that binary/test — see the next point.
- **`publishableKey`, not `anonKey`**: the `supabase_flutter` version in this project deprecated the `anonKey` parameter of `Supabase.initialize` in favor of `publishableKey` (same value works for either name — it's a rename, not a new key format). Use `publishableKey` in new code; passing the legacy anon JWT to it is correct and expected here.
- **Test bootstrap**: `test/widget_test.dart`'s top-level `setUpAll` calls `SharedPreferences.setMockInitialValues({})` then `Supabase.initialize(url: 'https://test.supabase.co', publishableKey: 'test-anon-key')` — a fake project, never the real one — purely so `BombaliSayilarGame` can construct its `SupabaseGameResultRepository` during widget tests without a `MissingPluginException` (shared_preferences has no real platform channel in test) or a "must initialize Supabase" assertion. No test asserts against real Supabase data.
- **Defensive save**: `GameController._persistResults` wraps each `saveResult` call in `.catchError((_) {})` (same "never let a side-service failure break game logic" pattern documented for `SoundService`/`SpeechService` above) — this is what keeps the "Completing both players..." test safe even though it runs against the fake test project (the write silently fails and is ignored) and what keeps a real player's game from breaking if Supabase is briefly unreachable.
- **Adding another game's persistence**: repeat this pattern (construct a `SupabaseGameResultRepository`-style class reading `Supabase.instance.client`, add a table + RLS policies to `supabase/schema.sql`) rather than introducing a second initialization path — `Supabase.initialize` is called exactly once, in `main()`, for the whole app.

### Android / APK derleme

The project also targets Android (`android/`, added with `flutter create --platforms=android --org io.github.ercinnn .`; app id `io.github.ercinnn.bombali_sayilar`, launcher label "Oyun Platformu"). Web remains the primary target — Pages is what gets deployed — but a sideloadable APK can be produced.

- **`flutter build apk` cannot run from this repo's own path.** The checkout lives under `C:\Projects\Eylül\…` and the "ü" breaks the Android build twice over: the Android Gradle Plugin refuses a non-ASCII project path outright, and setting `android.overridePathCheck=true` only pushes the failure one step later into the Dart AOT snapshotter (`Unable to read file: …\Eyl?l\…\app.dill`, exit 255) — so **don't** re-add that override, it was tried and reverted. Build from a copy on an ASCII path instead:
  ```bash
  robocopy <repo> <ascii-path> /E /XD build .dart_tool .git .idea /XF *.apk
  cd <ascii-path> && flutter pub get && flutter build apk --release
  ```
  The APK lands at `<ascii-path>/build/app/outputs/flutter-apk/app-release.apk`; copy it back next to the repo (root `*.apk` is gitignored). Renaming the repo directory to an ASCII name would remove this whole workaround.
- **`INTERNET` permission is in the main manifest on purpose.** Flutter's template only declares it in the debug/profile manifests, so a *release* APK without this line gets no network at all and Supabase (sign-in, saved results) fails silently at runtime while everything works fine in debug. Don't "clean it up".
- **Google sign-in on mobile needs the deep link.** On web, `signInWithOAuth` returns to the site itself, so `redirectTo` is null; on mobile the browser is a separate app and can only come back through `SupabaseConfig.mobileAuthRedirectUrl` (`oyunplatformu://login-callback/`). That exact string must match in three places: that constant, the `intent-filter` in `android/app/src/main/AndroidManifest.xml`, and Supabase's Authentication → URL Configuration → Redirect URLs (a dashboard step Claude can't do — see "Do not open the Supabase dashboard"). Until it is added there, the APK builds and runs but sign-in never returns to the app. The scheme is deliberately not the app id: URI schemes can't contain the underscore in `bombali_sayilar`.
- **The release APK is signed with the debug key** (Flutter's default `signingConfig = signingConfigs.getByName("debug")`). Fine for sideloading; a real keystore + `key.properties` is required before any Play Store upload.

### Deployment (GitHub Pages via GitHub Actions)

`.github/workflows/deploy.yml` builds and deploys the Flutter web app to GitHub Pages on every push to `main` (and via manual `workflow_dispatch` from the Actions tab). Two jobs: `build` (checkout → `subosito/flutter-action@v2` on the stable channel → `flutter pub get` → `flutter build web --release --base-href /oyun/` → `actions/upload-pages-artifact@v3`) then `deploy` (`actions/deploy-pages@v4`, needs the workflow's `pages: write` + `id-token: write` permissions).

- **`--base-href /oyun/` is load-bearing**: the site is served from `https://ercinnn.github.io/oyun/` (repo name `oyun`), not the domain root — a missing/mismatched base-href silently breaks every asset and route path once deployed to Pages, even though the exact same build works fine locally (served from `/`). If the repo is ever renamed, this flag must be updated to match, together with the Supabase Auth redirect URL below.
- **One manual, one-time step this environment cannot automate**: GitHub Pages must have its Source set to **"GitHub Actions"** in the repo's Settings → Pages (`github.com/ercinnn/oyun/settings/pages`) — there's no `gh` CLI or GitHub API token available here to flip that setting from code. Until a human does it once, `deploy-pages@v4` fails on every run even though the `build` job succeeds every time (confirmed via the public Actions API — `build` was green, `deploy` red, three runs in a row, before this was pointed out to the user). If the live URL 404s, check `github.com/ercinnn/oyun/actions/workflows/deploy.yml` first — a failing `deploy` step with a passing `build` step means this setting.
- **Supabase Auth redirect URLs must include the Pages URL**: `https://ercinnn.github.io/oyun/**` has to be in the Supabase project's Authentication → URL Configuration → Redirect URLs (alongside a `http://localhost:<dev-port>/**` entry for local testing), or Google sign-in fails on the live site with a redirect mismatch — this is a separate setting from the Google Cloud OAuth client's own authorized redirect URI (see "Kimlik doğrulama" above), which points at Supabase's `/auth/v1/callback` instead.

### Theming (`GameColorTheme` / `AppThemeController`)

- `models/color_theme.dart` defines `GameColorTheme` (name, `boxColor`, `backgroundColor`, `numberColor`), 5 fixed presets (`standardThemes`), and an 8-color palette (`customColorPalette`) shared by all three custom pickers.
- `controllers/theme_controller.dart` (`AppThemeController`) holds either a selected preset index or three independently-chosen custom colors; `current` resolves to the active `GameColorTheme`. It is intentionally a separate `ChangeNotifier` from `GameController` (theme picking happens in `SetupScreen` before/independent of game state) and is provided once per game session (scoped inside `BombaliSayilarGame`, see above) so it's a single shared theme for both players (per explicit product decision — not per-player), not shared with any other game on the platform.
- Only the **active** cell's colors come from the theme (`widgets/grid_cell.dart` reads `AppThemeController` for the `active` state only). Cleared (green) and locked (grey) cell colors are hardcoded on purpose — they're state feedback, not decoration, and must stay visually distinct regardless of the chosen theme.
- `theme.backgroundColor` is applied only to the `Container` behind the grid in `GameScreen`, not the app-wide `Scaffold`/`MaterialApp` background — this keeps default (black-on-white) text readable on the setup/results screens even when a saturated custom color is chosen.

### Grid sizing (`widgets/number_grid.dart`)

Cell size is computed in a `LayoutBuilder`, driven primarily by **available height** divided by 10 rows (not width) so all 10 rows are visible without scrolling on typical screens, clamped to `[_minCellSize, _maxCellSize]` and capped by width so 5 columns never overflow. It's built as a manual `Column`/`Row` of fixed-size `SizedBox`es (not `GridView`) wrapped in a `SingleChildScrollView` as a fallback for viewports too short to fit the clamped minimum. If you change row/column counts or spacing, this is the place that needs the math updated.

### Sound (`services/sound_service.dart`) and speech (`services/speech_service.dart`)

Sound effects (`assets/sounds/bomb.wav`, `assets/sounds/win.wav`) are synthesized locally by `tool/generate_sounds.dart` (no external/downloaded audio assets). `SoundService` loads them via `rootBundle` and plays them with `audioplayers`' `BytesSource` — **not** `AssetSource`. This is deliberate: on Flutter web, the built asset actually lives at `/assets/assets/sounds/*.wav` (pubspec assets are declared under a folder literally named `assets/`, and Flutter web additionally prefixes every asset with `/assets/`), which conflicts with `AssetSource`'s own `assets/` prefix and 404s silently. `BytesSource` sidesteps that entirely. `GameController` triggers `playBomb()`/`playWin()` directly (not the UI layer) so sound stays in sync with state transitions; both calls are wrapped in try/catch inside `SoundService` so a playback failure (e.g. browser autoplay policy) never breaks game logic.

`SpeechService` (used only by Kart Eşleştirme, see above) is a separate, unrelated service — text-to-speech via `flutter_tts`, not a bundled audio asset — because it needs to say arbitrary words in two languages rather than play one fixed clip. Follow the same defensive pattern if you add more speech: wrap every `flutter_tts` call in try/catch so an unsupported browser/OS never breaks the game.
